Stage 04: gene expression for the whole cohorts

For every person in MAGE (731) and Geuvadis (451), count the RNA reads from each gene on three references using the same raw reads: T2T-CHM13v2.0, GRCh38 and FixItFelix-patched GRCh38. The output is one gene × person table per reference and cohort, which is what stage 05 (eQTL mapping) reads. Every example below is a real file from this project.

·The problem and the design

The raw reads for one cohort are about 2.5 TB. Scratch is shared with t2t-atlas and filled up twice (2026-10-23 and 10-26). One run takes about 20 minutes on three references. So the reads can never all be on disk at once, and the work has to survive failures and restarts.

The solution is a conveyor belt: download a batch of 60 runs, process each run, keep only the small results, delete the reads, then move to the next batch.

1 make-cohort-sheets.py    which runs exist                       → config/samplesheets/<cohort>.csv
2 submit-cohort.sh         queue every batch, in a safe order     → logs/04-expression/submitted-*.tsv
   ├─ 3 fetch-sra-batch.sbatch   download 60 runs                → work/04-expression/sra/   (scratch, temporary)
   └─ 4 run-batch.sbatch         start Nextflow for that batch
        └─ 5 workflows/expression.nf       pick the runs to do
             └─ 6 QUANTIFY_RUN  reads → STAR + salmon × 3 references → results/04-expression/<cohort>/<run>/  (kept)
        8 delete the batch's downloads
9 merge-expression.py       all runs → one table per reference      → results/04-expression/<cohort>/matrices/

Inputs from earlier stages

  • config/samples/expression-individuals.tsv (stage 01): who has genotypes, so who is worth quantifying.
  • data/star-references/<ref>/ (stage 02): the STAR index, transcripts.fa, tx2gene.tsv, genes.tsv and keep-regions.bed for each reference.
  • The settings (STAR options, salmon mode) are those tested in the stage 03 pilot.

1Samplesheets: the to-do list

scripts/04-expression/make-cohort-sheets.py · run once, on the login node

This writes a table with one row per sequencing run, not per person, because some people were sequenced more than once. Everything downstream reads this table.

Command

pixi run python scripts/04-expression/make-cohort-sheets.py

What it does

  1. Reads expression-individuals.tsv and keeps people with included = yes (in the T2T genotype panel).
  2. MAGE: reads the ENA run report for PRJNA851328. Ancestry and sex come from sample_title. Read length = base_count / read_count / 2 = 150.
  3. Geuvadis: reads the ENA report for PRJEB3366 (strips the GEUV: prefix) and fills sex, ancestry and lab from the Geuvadis sample sheet E-GEUV-1.sdrf.txt. Read length 76.
  4. Sorts by run accession and cuts the runs into batches of 60: batch = row_index // 60 + 1.
  5. Writes the planned download path in the sra column.

Key code

    df["batch"] = df.index // args.batch_size + 1

2Submit the chain of jobs

scripts/04-expression/submit-cohort.sh · run on the login node, does no work itself

This submits two Slurm jobs per batch, a download job and a processing job, and links them with dependencies so they run in a safe order without you watching.

Command

bash scripts/04-expression/submit-cohort.sh mage            # all batches
bash scripts/04-expression/submit-cohort.sh mage 5 13       # only batches 5–13

The dependency rules

batch:     1            2            3            4
fetch:   F1 ────────► F2 ────────► F3 ────────► F4        F_k waits for F_(k-1) and R_(k-2)
          │            │            │            │
run:     R1 ────────► R2 ────────► R3 ────────► R4        R_k waits for F_k and R_(k-1)
  • Downloads stay one batch ahead. While batch 1 is processed, batch 2 downloads, so processing never waits for data.
  • At most about two batches of downloads on disk (~320 GB). F3 cannot start until R1 has finished and deleted batch 1's files.
  • One Nextflow controller at a time. R2 waits for R1.
  • Every dependency is afterany ("after it ends, success or not"). With afterok, one failed run would freeze the whole chain.

Key code

for ((k=FIRST; k<=LAST; k++)); do
  dep=""
  [[ -n ${F[$((k-1))]:-} ]] && dep="afterany:${F[$((k-1))]}"            # previous download
  [[ -n ${R[$((k-2))]:-} ]] && dep="${dep:+$dep,}afterany:${R[$((k-2))]}" # batch two back processed
  F[$k]=$(sbatch --parsable ${dep:+--dependency=$dep} fetch-sra-batch.sbatch $COHORT $k)
  dep="afterany:${F[$k]}"                                              # this batch downloaded
  [[ -n ${R[$((k-1))]:-} ]] && dep="$dep,afterany:${R[$((k-1))]}"      # previous batch processed
  R[$k]=$(sbatch --parsable --dependency=$dep run-batch.sbatch $COHORT $k)
done

3Download one batch

scripts/04-expression/fetch-sra-batch.sbatch · Slurm job t2t-fetch3, 6 CPUs, 8 GB, ≤ 12 h

This downloads the 60 runs of one batch from NCBI SRA, three at a time. A .sra file is NCBI's compressed read format, about 2–5 GB per run. It is turned into FASTQ only later, inside the processing task, so the large FASTQ exists for just a few minutes.

Command (usually submitted by step 2)

sbatch scripts/04-expression/fetch-sra-batch.sbatch mage 1

For each run

results complete?            → skip     (results/04-expression/<cohort>/<run>/complete.txt)
already downloaded+checked?  → skip     (<run>.validated exists)
scratch < 400 GB free?       → wait 10 min, check again
prefetch                       max 30 min per attempt, up to 100 attempts
vdb-validate                   NCBI's own checksums
write <run>.validated          "downloaded and checked" marker

Why each guard exists

GuardAdded after
30-minute limit per prefetch attempt (exit 124 = timed out; partial files removed, start again)2026-10-17: prefetch looped for hours at ~120 MB without failing
Wait while scratch has < 400 GB free (MIN_FREE_GB)2026-10-23: shared scratch reached 99%
Skip completed and validated runsso rerunning any batch is always safe
RetriesHTTPS connections from Karakoram to AWS S3 are often reset

Key code

while (( $(df --output=avail -BG $SRA | tail -1 | tr -dc 0-9) < MIN_FREE_GB )); do
  echo "$run waiting: scratch has … free" >&2; sleep 600
done
for i in $(seq 1 100); do
  rc=0; timeout 30m prefetch --max-size 100G -O $SRA $run || rc=$?
  [[ $rc -eq 0 ]] && break
  [[ $rc -eq 124 ]] && rm -f $SRA/$run/$run.sra.{tmp,prf,lock}   # timed out: start fresh
  sleep 10
done
vdb-validate $SRA/$run/$run.sra || return 1
date -u +%FT%TZ > $SRA/$run/$run.validated

4Start Nextflow for one batch

scripts/04-expression/run-batch.sbatch · Slurm job t2t-nf3, 2 CPUs, 8 GB, ≤ 3 days

This small job runs the Nextflow controller (the "head job"). The controller does no alignment. It submits one Slurm job per run, watches them, resubmits a failure once, and records what happened. When the batch is finished, the same script deletes the downloads (step 8).

Command (usually submitted by step 2)

sbatch scripts/04-expression/run-batch.sbatch mage 1
sbatch scripts/04-expression/run-batch.sbatch mage 1 test     # 2-run test (test-mage-2.csv)

Key code

LAUNCH=$ROOT/work/04-expression/launch/$COHORT-b$BATCH; mkdir -p $LAUNCH; cd $LAUNCH
nextflow run $ROOT/scripts/04-expression/nextflow/main.nf -profile slurm \
  --input $SHEET --batch $BATCH \
  -work-dir $ROOT/work/04-expression/nf-work/$COHORT -resume \
  -with-trace $ROOT/logs/04-expression/trace-$COHORT-b$BATCH-$SLURM_JOB_ID.tsv
  • Launch folder per batch (work/04-expression/launch/mage-b1/): Nextflow keeps its memory of a run there, so -resume continues the right batch.
  • Work folder (work/04-expression/nf-work/mage/): each task's scratch space.
  • Trace: one line per task with its time, CPU and memory, used for data/metadata/resource-usage.tsv.

5Pick the runs to process

scripts/04-expression/nextflow/workflows/expression.nf

Before any heavy work, the workflow checks its inputs and filters the samplesheet down to the runs that still need doing.

In order

  1. Stop early on bad input: the samplesheet must have sample, run, cohort, batch, read_pairs, read_length, sra, and genome.fa must exist for all three references.
  2. Keep this batch (or every row with --batch all).
  3. Drop finished runs: those with complete.txt.
  4. Drop runs with no validated download, with a warning instead of a crash, so one failed download does not stop 59 good runs.
  5. Package each remaining row as meta (id, sample, cohort, read_pairs, read_length) plus the .sra path, and send it to QUANTIFY_RUN.
  6. When all tasks end, collect every run's mapping-summary.tsv into results/04-expression/summaries/mapping-summary-batch<k>.tsv.

Key code

runs = channel.fromPath(sheet).splitCsv(header: true)
    .filter { row -> params.batch == 'all' || row.batch == params.batch.toString() }
    .filter { row -> !file("${params.outdir}/${row.cohort}/${row.run}/complete.txt").exists() }
    .filter { row ->
        def ok = file("${file(row.sra).parent}/${row.run}.validated").exists()
        if (!ok) log.warn "${row.run}: no validated .sra at ${row.sra}; skipped …"
        ok }
    .map { row -> tuple([id: row.run, sample: row.sample, cohort: row.cohort,
                         read_pairs: row.read_pairs as long, read_length: row.read_length as int], file(row.sra)) }
QUANTIFY_RUN(runs, refs)

6QUANTIFY_RUN: what happens to one run

scripts/04-expression/nextflow/modules/local/quantify_run/main.nf · one Slurm job per run, 16 CPUs, 48 GB

All three references are done in one task, so the reads are unpacked only once and the FASTQ never sits on disk between jobs.

Sequence

a  fasterq-dump  .sra → <run>_1.fastq + <run>_2.fastq        (task TMPDIR on scratch)
b  count pairs = lines / 4;  ≠ ENA read_pairs → FAIL           (catches corrupt or partial data)
c  for ref in chm13v2.0 grch38 grch38-ffx:
     STAR     → genome BAM + transcriptome BAM + ReadsPerGene.out.tab
     salmon   → salmon/quant.sf  (from the transcriptome BAM)
     samtools idxstats          → reads per chromosome
     samtools view -L keep-regions.bed → regions.bam  (key loci only)
     copy STAR logs; delete the genome BAM (~8 GB)
     add one line to mapping-summary.tsv
d  write complete.txt  LAST

a–b. Unpack and check the reads

fasterq-dump --split-files --threads 16 --temp $TMPDIR -O $TMPDIR/fq $sra
n=$(( $(wc -l < $TMPDIR/fq/${run}_1.fastq) / 4 ))          # a FASTQ record is 4 lines
[[ $n -eq ${meta.read_pairs} ]] || { echo "$run: $n read pairs, expected …" >&2; exit 1; }

This check found ERR204978 in Geuvadis: it has 5.27 M unpaired reads besides its pairs, so it failed the count. It got its own samplesheet and ran on its pairs only, as "batch 12".

c. STAR alignment

STAR --genomeDir $R/star-2.7.11b-oh${read_length-1} \
     --readFilesIn ${run}_1.fastq ${run}_2.fastq \
     --outFilterType BySJout --outFilterMultimapNmax 20 \
     --outFilterMismatchNoverReadLmax 0.04 --alignIntronMax 1000000 … \
     --outSAMtype BAM SortedByCoordinate \
     --quantMode TranscriptomeSAM GeneCounts
  • The index matches the read length: MAGE 150 bp → oh149, Geuvadis 76 bp → oh75 ("overhang" = read length − 1, built in stage 02).
  • GeneCounts: STAR counts, per gene, the read pairs that map uniquely and fall in exactly one gene. These are the main expression numbers.
  • TranscriptomeSAM: also writes the alignments in transcript coordinates, which salmon reads next.
  • Same options as the stage 03 pilot (ENCODE-style settings).

c. salmon

salmon quant -l A -t $R/transcripts.fa -a $TMPDIR/$ref.Aligned.toTranscriptome.out.bam -o $O/salmon

Salmon is the second counting method. Unlike STAR GeneCounts, it shares out multi-mapping reads between transcripts by likelihood instead of dropping them. Comparing the two shows whether a T2T effect depends on how multi-mapping reads are handled.

c. Keep a little of the alignment

samtools idxstats  genome.bam > idxstats.tsv
samtools view -b -M -L $R/keep-regions.bed -o regions.bam genome.bam
rm -f $TMPDIR/$ref.Aligned.*

The genome BAM (~8 GB per reference) is too big to keep for 1,400 runs × 3 references. Only reads in keep-regions.bed (the candidate genes and their false copies ±100 kb, plus the MHC; stage 02) are kept, about 45 MB, so the key loci can be inspected later without realigning.

d. Finish

echo "end $(date -u +%FT%TZ)" >> ${run}/log.txt
date -u +%FT%TZ > ${run}/complete.txt
Why complete.txt comes last. If the job dies at any point before this line, there is no complete.txt, and the run is redone next time. A half-finished run can never be mistaken for a finished one. Every script in this stage uses this one file to decide "done or not".

9Merge into gene × person tables

scripts/04-expression/merge-expression.py (+ merge-expression.sbatch) · once per cohort, after all batches

This turns about 780 separate run folders into the tables stage 05 needs.

Command

sbatch scripts/04-expression/merge-expression.sbatch geuvadis
# or directly:
pixi run python scripts/04-expression/merge-expression.py --cohort mage

What it does

  1. Reads the samplesheet and marks each run included if it has complete.txt.
  2. Writes runs.tsv: every run, whether included, and its mapping percentages per reference.
  3. For each reference (three in parallel):
    • STAR: column 2 of ReadsPerGene.out.tab, dropping the four N_ rows.
    • salmon: quant.sf → map transcript → gene with tx2gene.tsv → sum per gene.
    • Put the genes in the order of genes.tsv; a gene missing in a run gets 0.
    • Combine runs of the same person: counts are summed, TPM is averaged.

Key code

def star(path):
